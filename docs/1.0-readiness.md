# Is `typedb` ready to be frozen at 1.0?

**Recommendation: `0.11.0` narrowing the surface, then `1.0.0-rc.1` from that
commit.** Nothing in the driver's behaviour blocks 1.0. Ten function heads are
published that should not be, and narrowing after 1.0 costs a major, so they are
worth one more `0.x` release. After that the surface is defensible as frozen.

> **Status, 2026-09-29: the narrowing is done** and is in `CHANGELOG.md` under
> `[Unreleased]`, awaiting the `0.11.0` release. All ten heads listed below are
> now `@doc false`; the surface is **198 public heads and 53 marked internal**,
> where this review found 208 and 43. Each row of the table in *What to narrow*
> is marked ✅. The rest of this document is unchanged and still describes the
> surface as reviewed.

*Written 2026-09-29 against `typedb` 0.10.4 (`main` at `ebd715e`) and TypeDB
3.12.1. Every count here was measured by loading the compiled application and
filtering modules exactly as `test/typedb/api_snapshot_test.exs` does, not read
off the source.*

## The surface, measured

| | as reviewed | after the narrowing |
| --- | ---: | ---: |
| published modules | 37 | 37 |
| public function heads | 208 | **198** |
| `@doc false` heads inside those modules | 43 | **53** |

"Published" is what ex_doc publishes: `@moduledoc false` modules —
`TypeDB.Transport`, `TypeDB.Token`, `TypeDB.Wire`, `TypeDB.Bang` and the rest —
are not in the count and are not promises. Heads, not names: `query/3` and
`query/4` are two, because a caller can break on either.

Since this review, `test/api_snapshot.txt` marks the 43 internal entries with a
trailing `# @doc false`, so the frozen promise is the lines without that marker.
Before, the file listed both alike, and twice in one week a `@doc false` helper
turned the snapshot red and was restructured as though it had widened the API.

not need a new one in front, the return shape is `{:ok, _} | {:error,

## What to narrow before the freeze — ten heads

Each of these was documented, so hiding it is breaking under this project's own
rule ("the public API is every documented module and function on hexdocs"). That
makes the list a `0.11.0`, not a patch, which is why it landed as its own change
rather than inside this review. **All ten are now `@doc false`** — see
`CHANGELOG.md` under `[Unreleased]` for the migration line for each, and for why
every one of them is `@doc false` rather than `@deprecated`.

| head | why it should not be a promise | what a caller uses instead |
| --- | --- | --- |
| ✅ `TypeDB.Concept.decode/1` | decodes one wire entry. `TypeDB.Answer.decode/1` and `TypeDB.ConceptRow.decode/1` do the same job one level up and are already `@doc false` — the three should agree. | concepts arrive already decoded from `ConceptRow.get/2` and `Answer.rows/1` |
| ✅ `TypeDB.Config.url/2` | builds `base <> "/" <> api_version <> path`. CONTRIBUTING says which HTTP requests a call makes is explicitly *not* covered by the version number; this is that mechanism, published. | `TypeDB.Connection.request/4` takes the path |
| ✅ `TypeDB.Config.raw_url/2` | same, for the unversioned endpoints | same |
| ✅ `TypeDB.Config.backoff/2` | the retry delay for attempt *n*. Retry policy is named in CONTRIBUTING as free to change. | `:retry_backoff`, `:retry_max_delay` |
| ✅ `TypeDB.Options.query_payload/1` | turns options into TypeDB's request body. The body is the server's shape, not ours. | pass options to `TypeDB.query/4` |
| ✅ `TypeDB.Options.query_payload/2` | same | same |
| ✅ `TypeDB.Options.transaction_payload/1` | same | pass options to `TypeDB.Transaction.open/4` |
| ✅ `TypeDB.Options.transaction_payload/2` | same | same |
| ✅ `TypeDB.HTTP.Req.request_options/6` | its own docstring gives the reason it is public: "so that the merge below can be asserted on directly". A `@doc false` function can be asserted on just as directly, and `Finch` and `Httpc` publish no equivalent — the asymmetry is an accident of which adapter got a test. | nothing; the test keeps working |
| ✅ `TypeDB.Connection.renew_token/2` | the second argument is a monotonic millisecond or `:any`, an internal protocol between `Transport` and `Connection` for telling "my token is stale" from "someone already replaced it". | `TypeDB.Connection.token/1`, which renews when needed |

That is 208 heads down to 198 — measured after the change, not predicted.
Nothing is removed, nothing changes shape, and no caller of the documented API
has to edit anything.

Two things this list deliberately does **not** contain:

- **`TypeDB.Connection.request/3,4`, `token/1`, `config/1`.** An escape hatch for
  endpoints the driver does not wrap is worth promising; an application that
  needs one and does not have it writes something worse.
- **`TypeDB.Error.new/2,3` and `from_response/2`.** Anyone writing an HTTP
  adapter builds errors, so these are part of the `TypeDB.HTTP` behaviour's
  usable surface even though the behaviour does not name them.

## What is out of 1.0

- **Several servers, routing, failover.** Decided and recorded in
  `docs/cluster-1.0-decision.md`: out. Clustering in TypeDB 3.x is alpha and
  Cloud/Enterprise only, CE is single-node, and replica discovery and primary
  routing belong to the gRPC drivers. `TypeDB.Server.servers/1` stays as a
  read-only view of membership. Tracked as `tdb-aoh.7`, which is open and does
  not block: a 1.0 that says "one connection, one server" is a complete promise,
  and adding addresses later is additive.
- **The return shape of `TypeDB.Transaction.analyze/3`.** The one documented
  exemption from SemVer, stated on the function and in CONTRIBUTING.
- **TypeDB's own wire format, error codes and behaviour.** When the server
  changes what it returns the driver reports the change rather than absorbing
  it. `test/api_snapshot.txt` cannot see this and is not meant to.
- **Message text.** Log lines, `Exception.message/1`, error prose. Branch on
  `:kind` and `:code`.
- **Which HTTP requests a call makes.** Retry policy, token renewal, connection
  reuse — all free to change; only the observable result is not.

## The 1.0-labelled work

Measured from `.beads/issues.jsonl`: **53 beads carry the `v1.0.0` label and all
53 are closed.** Four beads are open and none of them carries the label:

| bead | what | blocks 1.0? |
| --- | --- | --- |
| `tdb-aoh` | epic: parity with the Rust driver as the coverage yardstick | **no.** A parity epic is a backlog, not a release gate; its one open child is the cluster one below. |
| `tdb-aoh.7` | cluster: several addresses, routing, failover | **no.** Decided out — `docs/cluster-1.0-decision.md`. Additive later. |
| `tdb-7hy` | raise cowlib/gun when the CVE fix ships | **no**, and not this package: it is `typedb_grpc`'s dependency tree. Re-measured 2026-09-12 — cowlib 2.20.0 exists, `grpc` still pins `gun ~> 2.4.0`, and the flagged paths are unreachable through this driver. |
| `tdb-c3h` | batch `Transaction.Client.reqs` into one message | **no**, and also `typedb_grpc`. A performance change needing a before/after measurement. |

So the ledger is clean: no open bead stands between the driver and a frozen API.

## Why now, and the one stale claim

`typedb/CONTRIBUTING.md` says 1.0 "will be made once the API has survived real
use rather than before", and gives as the reason that "no application has yet
met the API". That sentence is out of date. Audit III and Audit IV were both
conducted *through* a real application by reading how it uses the driver and
treating each workaround it had written as evidence of something missing —
`Answer.truncated?/1`, `running?/1` and
`create_database_if_not_exists/3` in 0.7.0, and TSV12 joining `retryable_codes/0`
in 0.8.0, all came from that. `noetic_knowledge` depends on `typedb` today. The
precondition the project set for itself has been met; the prose should be
updated to say so rather than continuing to say the opposite.

## Recommendation

1. **`0.11.0`** — the ten `@doc false` moves above, and nothing else. ✅ Done:
   the snapshot diff is ten lines gaining the marker and nothing else, which is
   exactly what the marker was added to make readable.
2. **`1.0.0-rc.1`** from that commit. An rc is what turns "we think this is
   frozen" into a thing an application can depend on and report against, and it
   costs nothing to cut.
3. **`1.0.0`** once the rc has been resolved by `noetic_knowledge` and its suite
   has run green against it. That is a day's work, not a quarter's — the driver
   has been tested against a live 3.12.1 all along, and the rc exists to catch
   what only a dependent's compile can catch.

The thing not to do is cut 1.0.0 directly from 0.10.4. Not because anything is
wrong with it, but because ten heads would be frozen that nobody meant to
promise, and the only way out of that afterwards is 2.0.0.
